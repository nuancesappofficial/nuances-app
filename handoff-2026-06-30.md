## Card Recovery Behavior

- Rebuilding or reinstalling resets the local WatermelonDB app sandbox.
- Saved cards will return only if they were already synced into Supabase
  `cards`, then pulled by the startup/auth sync.
- Local-only cache cards intentionally do not return after reinstalling.

## Cache Sync Enforcement

- `cached_items` is a device-only WatermelonDB table:
  - client sync neither queries nor writes `public.cached_items`;
  - pull and push transforms always remove `cards.cached_item_id`;
  - raw WatermelonDB change sets are not logged because they can contain cache
    text, OCR output, and local media paths.
- `20260630_disable_remote_cache_sync.sql` purges legacy remote cache rows.
- `20260701000001_enforce_local_only_cache.sql` is the required final lockdown:
  - removes every RLS policy on `public.cached_items`;
  - revokes all table privileges from `anon` and `authenticated`;
  - prevents legacy clients from persisting `cards.cached_item_id`;
  - purges rows that raced the first cleanup.
- The follow-up migration must be deployed before the server-side guarantee is
  active. Strict lockdown intentionally makes legacy app builds that still push
  `cached_items` fail sync; those builds must be retired or force-updated.
- The `cached-images` Storage bucket is used only after a card is explicitly
  saved. It stores the saved card-detail image, not the local cache stack.

## Account Isolation

- Auth transitions are serialized and stale A-to-B bootstrap work is ignored.
- The previous navigator is unmounted before sign-out/account-switch cleanup.
- WatermelonDB scope changes wait for any active sync and reset the global sync
  cursor before another account is displayed. Rows remain locally partitioned
  by `user_id` so an offline, not-yet-uploaded card is not destroyed on logout.
- Every card/cache list query is filtered by the active `user_id`; card/cache
  mutation entrypoints revalidate the record owner against the persisted local
  session before writing. Remote writes remain protected by JWT-backed RLS.
- Settings, card-image maps/files, share-ingest logs, and mistake logs use
  account-scoped keys or directories.
- The iOS Share Extension queue carries `owner_user_id`; ownerless or
  mismatched content is discarded instead of being imported into another
  account.

## Saved Card Cloud Persistence

- Newly saved cards receive a UUID before their first WatermelonDB insert, so
  the local and Supabase primary keys are identical.
- Card creates use idempotent Supabase upserts. Save Card hands the durable
  local transaction to a background sync, which then queries Supabase to confirm
  every card ID exists under the same authenticated owner.
- Failed/offline sync remains in WatermelonDB's durable change queue and is
  retried at startup, authentication, and foreground activation. Upload and
  verification are intentionally invisible and never block the Save button.
- Startup and Auth triggers share the same in-flight/freshness gate, foreground
  sync is skipped for two minutes when there are no pending mutations, and card
  creates/deletes/tag changes are debounced into one background batch.
- Each actual sync attempt performs one remote `getUser()` verification, then
  uses local session checks between phases while Supabase RLS remains the final
  authorization boundary.
- Startup/auth backup begins immediately after the account scope is established;
  it is deliberately ordered before RevenueCat entitlement bootstrap so a
  subscription-service outage cannot suppress card backup.
- Sync scope v4 performs a one-time true full pull for upgraded installations.
  `forceFullSync()` now clears both WatermelonDB pull-cursor keys before syncing;
  previous builds used that name without actually resetting the cursor.
- Cloud pulls are paginated so accounts with more than the PostgREST row limit
  are complete. Migration `20260701000003_add_sync_server_timestamp.sql`
  supplies the PostgreSQL clock for the Watermelon cursor, preventing a fast
  device clock from skipping later cloud writes.
- Created rows are pushed in bounded idempotent upsert batches, so a lost HTTP
  response cannot turn a successful insert into a duplicate-key retry failure.
- Pre-UUID cards created by older app versions are upgraded before sync. The
  upgrader reuses a matching remote UUID when possible, otherwise creates a
  stable UUID, and remaps review/local preference references before deleting
  the obsolete short-ID row.
- Saved-card images use an account-scoped durable upload queue. A job is removed
  only after Storage upload, card sync, and a remote owner/image-path readback
  all succeed. Multiple pending images upload first and then share one card sync.
- Share Extension ingestion writes only local `cached_items` and never triggers
  cloud card sync.
- `20260701000002_harden_card_account_isolation.sql` adds explicit per-operation
  card RLS policies and a trigger that prevents authenticated clients from
  changing `user_id`.
